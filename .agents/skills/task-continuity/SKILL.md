# Task / Branch Continuity

Use this skill before creating a new implementation branch when work may already exist, and whenever a coding session is resumed after interruption, handoff, model switch or lost chat context.

## Source-of-truth order

When sources disagree, use:

1. current repository source, Git history, tests and GitHub PR/check state,
2. active task state from the control plane when available,
3. `docs/CURRENT-HANDOFF.md`,
4. chat/session memory.

Never create or switch branches because a model merely remembers one.

## Open branch is not an active task

An open branch may be stale, abandoned, superseded, generated by automation or owned by another task. Before acting:

1. identify the user outcome or requirement ID,
2. inspect matching open PRs and branches,
3. compare the candidate branch with current `dev`,
4. inspect PR status/checks and the recorded next step,
5. resume only when the evidence matches the requested task.

If no valid active task exists, create a new focused branch from current `dev`.

## Durable task binding

For non-trivial work, bind one task to one writable branch and one PR:

`task → repository → branch → PR`

Create a draft PR early, before a long implementation session. Record the branch, PR, status and next safe step in Current Handoff using the machine-readable task-state block described in `docs/TASK-LIFECYCLE.md`.

## Resume protocol

Before modifying code after an interruption:

1. read Project Memory and Current Handoff,
2. parse/validate task state,
3. inspect the referenced PR and branch,
4. verify the branch still exists and is not already merged/superseded,
5. compare it with current `dev`,
6. inspect the latest commit SHA and relevant checks,
7. confirm the recorded next step is still valid,
8. continue from verified state or explicitly retire/rebind the task.

Do not repeat completed external writes or identical failed repair loops.

## Writer ownership

Without a central control-plane lease service, keep one modifying agent per task branch. Parallel reviewers may read the same branch. Parallel implementers must use separate branches/worktrees and integrate through PRs.

When the future AI Control Plane provides leases, treat its active lease as the write-ownership record, but still revalidate GitHub state before writing.

## Checkpoints

Update task state after meaningful boundaries:
- branch created,
- draft PR created,
- implementation checkpoint committed,
- checks run,
- review finding confirmed,
- repair committed,
- ready to merge,
- blocked/interrupted.

Do not update it for every small edit.

## Completion

Before merging a completed task PR into `dev`, reset `docs/CURRENT-HANDOFF.md` to the idle task-state template so the integration branch never inherits stale active-task state.

After merge:
- verify the PR is merged,
- verify the temporary branch is removed by GitHub native automatic head-branch deletion or remove it safely,
- mark the task complete in the external control plane when present,
- do not continue work on the deleted/superseded branch.
